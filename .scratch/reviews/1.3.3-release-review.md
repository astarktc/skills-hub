## Findings, ranked

### F1 — P2: L5 reintroduces the shared-guard polling flake L2 removed

**Location:** `src-tauri/src/core/tests/project_sync.rs:2747–2756`, called by `a_listing_says_whether_its_reconcile_pass_rewrote_a_status` at `:2760–2799`.

`reconciled_listing` retries the production `try_serialized` listing **100 × 50 ms** against the process-global mutation guard. Other concurrently running tests legitimately hold that guard. The new test is therefore not guaranteed to reach the uncontended reconciliation branch within its five-second budget.

**Fresh reproduction, unchanged checkout:**

```text
npm run version:check && npm run check
  PASS — 1,321 frontend tests; 921 Rust tests, 1 ignored
cd src-tauri && cargo test --all
  FAIL — 920 passed; 1 failed; 1 ignored
  core::project_sync::tests::a_listing_says_whether_its_reconcile_pass_rewrote_a_status
  src/core/tests/project_sync.rs:2756:5: reconcile pass never got the guard
cargo test --all a_listing_says_whether_its_reconcile_pass_rewrote_a_status -- --nocapture
  PASS — 1 passed, 921 filtered out, 0.02 s
cargo test --all
  PASS — 921 passed; 0 failed; 1 ignored, 41.82 s
```

This demonstrates test contention, not a broken `rewrote_statuses` calculation. It still makes the pre-release gate nondeterministic. L2/#100's brief specifically says to isolate no-contention tests rather than lengthen polling or make the production reader block.

**Concrete fix:** wrap this test's setup and assertions in `mutation_guard::with_private_guard` (`src-tauri/src/core/mutation_guard.rs:53–65`) and replace the polling helper with a direct listing plus `assert!(listing.reconciled)`. Keep production `try_serialized` nonblocking and retain separate tests of the held-guard/skipped branch. Rerun both full gates after the change. Do not mark it fixed merely because the rerun or hosted CI passed.

### F2 — P3: global overwrite drops the new removal-permission condition

**Locations:** `src-tauri/src/core/global_sync.rs:157–196`, particularly the I/O-chain classifier at `:180–195`; new producer `src-tauri/src/core/sync_engine.rs:471–487`; old copy `src/i18n/resources.ts:199–200`.

The removal primitive intentionally preserves the underlying I/O error underneath `SignalError::RemovalPermissionDenied`. The global-sync classifier subsequently scans that same chain for `PermissionDenied`/Windows error 5 and converts it into `GlobalSyncError::ToolNotWritable`, discarding the new condition and its exact failed-removal path. The batch then treats it as a skipped unwritable harness, not the new removal failure.

For example, a writable harness skills root can contain an existing nonempty target directory whose children cannot be removed. An overwrite reaches the new typed removal failure, but this wrapper tells the operator the **harness root** has a permission problem and suggests running as administrator. It loses the ownership/read-only/other-process guidance and retry caveat implemented for Delete, Disable and project removals. EROFS and Windows 19/32 do not necessarily follow this same older classification, so equivalent removal failures can also differ by OS error code.

**Evidence level:** direct source trace, not a claimed end-to-end reproduction. An attempted external probe could not access the crate-private `core` module; no source visibility was changed to make it run. Ordinary safety/refusal behavior is unaffected, and the original #76 brief explicitly used global sync's existing typed error as precedent, so this is a follow-up rather than a release blocker.

**Concrete fix:** before the generic I/O fallback, preserve an already-classified `SignalError::RemovalPermissionDenied` as `GlobalSyncError::Other(err)` so the existing settlement downcast exports `REMOVAL_PERMISSION_DENIED`. Keep `TOOL_NOT_WRITABLE` for genuine root-creation/write failures. Add a global-batch overwrite test with a writable root and an undeletable occupant; assert the exported code, exact occupant path, report classification and unchanged bytes. Pin Windows 5/19/32 classification separately where the CI platform can execute it.

State the supported development/test Node baseline consistently with AGENTS.md/CI, and distinguish Windows operator validation from hosted CI instead of claiming none. No registry-row change is requested: roster/path corrections remain round-20 work.

## Upgrade and removal safety

### Existing 1.3.2 database

- `SkillStore::ensure_schema` invokes the WAL policy before the schema transaction. This is a persistent journal-mode change, **not a schema/version change or a skills rewrite**. Each connection explicitly applies the 30-second busy timeout, `synchronous = FULL` and foreign keys before doing its work.
- The new upgrade test starts with a rollback-journal database containing a skill, upgrades it, checks WAL and preserves that skill; separate tests pin FULL, reader snapshot isolation, four Refresh-shaped workers and eight-worker headroom. These ran in the fresh gate and exact-head Windows CI.
- Journal-mode conversion errors are logged, allowing the existing mode to continue; this is not a promise that every filesystem/open failure is recoverable. A later schema/read failure can still fail startup as before.
- Legacy-identifier adoption is **not** the normal 1.3.2 → 1.3.3 path: the app identifier/database path is unchanged and an existing database containing skills returns before adoption. The new backup copies the target DB/sidecar set before removing originals, restores removed files best-effort on removal failure, and does not leave old sidecars beside the adopted DB. Crash-snapshot and failed-copy tests passed. This is not an atomic rename of a multi-file set, and the tests do not establish power-loss durability of those backup copies or safety with a second app process modifying them.
- **Downgrade:** 1.3.2 uses the same bundled `rusqlite`/SQLite dependency and does not force rollback mode. It can open a WAL database; no new schema prevents it. Its five-second timeout policy returns, so its older contention behavior can return too. No installed 1.3.2 binary was launched against a 1.3.3 database in this review. Do not manually copy only the DB file while WAL writers are active or delete sidecars to “downgrade.”

### Ordinary operator filesystem layout

- For `~/.claude/skills/alpha -> ~/.skillshub/alpha`, the **leaf link is not resolved** for removal. Its parent remains outside the protected Library, so Disable/unassign unlinks it rather than deleting the referent. A real copied target outside the Library is admitted after the subtree check.
- A harness root linked somewhere else is not categorically forbidden: a leaf under an external non-Library root can still be removed. A root linked **onto the Library** is intentionally refused when the target is the Library's real directory, including case aliases. The configured root's whole subtree and historical recorded copies are protected.
- Delete's own central-copy removal is a separate, record-authorized exception. It excludes the same skill from the “other copies” overlap check, but still refuses the library root, ancestors, other copies, and mounts. It therefore does not make normal Delete impossible simply because all central copies are protected.
- Update/Refresh acquisitions now pass the Library fence to cache retries; Propagation passes it to target replacement. Healthy same-link targets still take the non-replacement path. The central finalization/staging machinery is not converted into target removal by this change.
- Cache age-out admits the cache root from the app-cache boundary through real directories, refuses root/Library overlap, and applies the fence to individual candidates. It deliberately refuses aliased app-owned cache directories rather than deleting through them. Individual failed removals are still skipped by cleanup's existing count-only API; not every cleanup refusal produces an operator-facing path message.
- Launch relocation is still unwired. Failure to resolve the configured central root causes **git-cache cleanup to be logged as skipped**, not startup failure from that new cleanup block. Existing temp cleanup and Explore-cache wiping remain; they are not newly fenced here. A guarantee that *every recursive removal anywhere in the app* has been converted would be too broad.
- The fence explicitly accepts a check/use race with other processes. Unix mount tests exercise device/identity and Linux mount-table handling through deterministic seams; the privileged real-bind-mount test remains ignored by the ordinary gate. No real mount or operator-directory destructive test was performed.

## Windows assessment

- New registry joins append components, yielding native separators. Previously stored mixed-separator paths remain accepted by Windows `Path` component parsing and filesystem APIs. No destructive path-string migration or automatic deployment relocation is introduced. The adapter registry's actual destinations/roster are unchanged.
- The app-data identifier/path is unchanged. WAL adds sidecars next to the DB under the app data directory; an ordinary per-user writable local `%APPDATA%` layout permits them. This is not a validation of redirected/network `%APPDATA%`, which has additional SQLite shared-memory/locking constraints. Rollback journaling already required directory writes; the patch does not request elevation.
- Junctions and directory symlinks remain link entries; the admitted physical leaf is removed with the Windows directory-link branch, never recursed through. Exact-head hosted Windows logs show the junction removal, dangling junction, overwrite, Disable and referent-preservation tests passing. File/dangling-symlink tests also report success, though privilege-dependent creation branches can skip internally; this is not an installed-app smoke.
- `is_permission_denied` covers the permission kind, EROFS/`ReadOnlyFilesystem`, and Windows raw errors **5/19/32**, with raw-code matching gated to Windows so Unix EIO=5 is not misclassified. The global-sync wrapper caveat is F2.
- Windows CI's four/eight-worker store tests ran without a `--skip` exclusion. It validates x64 test execution, not a packaged Arm64 installation or native Windows UI behavior.
