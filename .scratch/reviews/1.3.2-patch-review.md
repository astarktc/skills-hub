## Findings

### F1 — P1: the new Windows gate excludes a real acquisition-fidelity defect, not five faulty tests

**Locations:** `.github/workflows/ci.yml:89–106`; production origin: `src-tauri/src/core/git_fetcher.rs:64–82, 498–505`; downstream: `core/git_acquisition.rs:271–288`, `core/content_identity.rs:95–123`.

**Status:** pre-existing production behavior, newly exposed and deliberately excluded by this patch. The CI comment is honest, but exclusion is not a correctness fix.

The CLI inherits `core.autocrlf`; the libgit2 path calls `Repository::clone` and later `checkout_tree` without installing an application-owned checkout policy. A GitHub Contents acquisition writes downloaded bytes, whereas a clone can check out different bytes for the same commit. A transport fallback can therefore change the installed skill without any upstream change.

**Fresh reproduction, in the reviewed worktree:**

```sh
cd src-tauri
GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.autocrlf GIT_CONFIG_VALUE_0=true \
  cargo test core::git_acquisition::tests -- --nocapture
```

Output: **45 passed, 5 failed** — exactly the five names excluded by the Windows job. Representative failure at `core/tests/git_acquisition.rs:1468`:

```text
left:  "---\r\nname: beta\r\n---\r\n"
right: "---\nname: beta\n---\n"
```

Changing only the injected value to `false` gives **50 passed, 0 failed**. This reproduction runs the real acquisition path, not a rewritten fixture assertion.

**Consequences, carefully bounded:**

- Content identities really differ: `hash_dir` feeds the raw file bytes into SHA-256. A clone-derived copy and an API-derived copy of the same committed skill need not compare `Same`. This can introduce unnecessary collision/overwrite review or prevent byte-identical import cleanup.
- An Update can churn central and propagated bytes merely because the acquisition strategy changed. Successfully propagated copies get their new hash recorded, so I do **not** claim this inevitably leaves them permanently “out of date.” Failed/unrefreshed copies can differ from the new central identity despite no upstream commit change.
- I found **no line-ending-only Invocation Edit conflict**: `skill_edits.rs:175–180` compares parsed invocation modes, not the raw saved lines. Its base snapshot changes, but CRLF alone does not satisfy `disagrees`.
- The byte difference is not limited to Markdown; clone checkout applies to scripts too. Normalizing only the tests' expected strings would conceal it.

**Smallest correct fix:** pin the app's Git checkout policy to `core.autocrlf=false` in both CLI and libgit2 acquisition, then remove the five exclusions. Apply the CLI override to **all** working-tree-producing commands, not just initial clone: checkout/reset and sparse reshaping matter too. Configure libgit2 **before initial checkout**, as well as existing-repository checkout. Add an ambient-`true` regression that exercises both adapters. See the policy section below for existing cache and `.gitattributes` caveats.

### F2 — P2: persistent failure headlines accumulate; a later run does not replace them

**Locations:** `src/hooks/useStatusReporter.ts:625–634` and `:71–78`; `src/App.tsx:631`.

The run toast passes `persist`, but no `id`. Sonner assigns a new ID to every call. The reporter dismisses toasts when opening Notifications (`:476`, `:539`), but not when a subsequent run starts or settles. Previously these warning headlines expired; now old failures remain indefinitely unless individually dismissed or the panel opens.

`visibleToasts={3}` is a visibility limit, **not eviction**. Sonner computes `index + 1 <= visibleToasts` and skips its expiration effect for `duration === Infinity` (`node_modules/sonner/dist/index.mjs:456, 582`). More than three persistent failures remain in the active collection. A later success does not clear them; when it fades, stale failure headlines remain/re-emerge.

**Reproduction against the installed Sonner, no browser or app launch:**

```sh
bun --eval 'import {toast} from "sonner";
const ids=[1,2,3,4].map(n=>toast.warning(`failed run ${n}`,{duration:Infinity,closeButton:true}));
toast.success("later success",{duration:2000});
console.log(toast.getToasts().map(t=>({id:t.id,title:t.title,persistent:t.duration===Infinity})));
console.log(new Set(ids).size);'
```

Output: four distinct persistent failure IDs (`1` through `4`), plus success ID `5`; distinct failure ID count **4**. The reporter's precise trace reaches the same calls without an ID or dismissal.

**Smallest correct fix:** make the run-headline channel replace its previous toast while preserving every `recordRun` history block. Either remember and dismiss the previous run-toast ID, or use a dedicated stable run-toast ID. With a stable ID, explicitly clear an absent action/description when replacing it: Sonner merges updates, so an old “View report” callback must not survive on a newer headline. Add a hook test for failure → failure → success and for panel-open dismissal. Do not reuse the lifecycle-refusal ID or erase notification history.

## Pre-existing P0 safety boundary — not a new patch regression

**Locations:** `src-tauri/src/core/sync_engine.rs:421–449`; `core/tool_adapters/mod.rs:868–878`; existing artifact-removal and overwrite callers. Owner: BACKLOG #88.

The requested universal statement “never follows a symlinked parent into central” is **false**. `symlink_metadata` does not follow the **leaf**, but path resolution follows ancestors. For:

```text
central/skill/nested/keep      real central bytes
tool-root -> central          directory symlink / junction
remove_path_any(tool-root/skill)
```

metadata describes the real `central/skill` directory. `ft.is_symlink()` is false, `ft.is_dir()` is true, and `remove_dir_all` deletes the central skill. A lexical tool-root fence does not prevent this.

**Fresh differential probe:** copied the exact `remove_path_any` bodies from `19e896c` and `736a437` into a standalone temporary crate, and ran:

```sh
cargo test --offline --manifest-path \
  /var/folders/6p/j8hvzsjx4wjf__r2jbgbff980000gn/T/skills-hub-132-review-ggp3onu6/Cargo.toml \
  -- --nocapture
```

Both versions printed:

```text
real leaf beneath parent aliased to central: CENTRAL SKILL DELETED (pre-existing)
```

The probe asserted that the parent alias remained and the central nested file was gone. Conversely, a **leaf link** below an aliased parent was removed without touching its referent. This is exactly the distinction the review must preserve.

**Correct fix belongs to #88:** admit destructive operations using physical entry identity (canonical parent plus leaf, without resolving the leaf link), explicit protected-central boundaries, and source/destination identity checks before overwrite/removal. Keep the launch relocation call disabled until that work is complete. A blanket conversion to `remove_dir`, or canonicalizing the whole path and deleting it, is not a fix.

## Removal matrix and test sensitivity

`remove_path_any` at `:421` uses one non-following leaf metadata read; the only new production branch is Windows `is_symlink_dir()` → `remove_dir` → return.

| Shape | Unix result | Windows result / evidence |
|---|---|---|
| Symlink to directory | `remove_file` unlinks leaf; referent intact. Fresh differential probe passed. | Directory-link metadata → `remove_dir`. New directory-symlink test passes in CI, but can early-return if creation is forbidden. |
| Symlink to file | `remove_file`; fresh probe preserved target bytes. | `is_symlink_dir=false` → `remove_file`; unchanged branch. No dedicated new Windows file-link test. |
| Dangling symlink | Leaf metadata succeeds; unlink works. Fresh probe and existing broken-symlink test passed. | The link's own directory/file attribute selects `remove_dir`/`remove_file`, independent of destination existence. Dedicated dangling directory/file-symlink tests are still absent. |
| Junction | Not a Unix filesystem shape. | New real-junction tests use `try_junction`, assert junction presence, then exercise removal, Disable/Delete settlement, overwrite, and identity. All nine junction-module tests report success in Windows CI. |
| Dangling junction | Not applicable. | New `a_dangling_junction_is_present_and_removed` passed in Windows CI. |
| Real nonempty directory | `remove_dir_all`, unchanged; fresh probe also verified an internal symlink does not cause traversal into central. | Same existing recursive removal path, unchanged. Existing file/dir/missing test is cross-platform. |
| Real file | `remove_file`, unchanged; fresh probe passed. | Same unchanged branch, covered by the existing basic test. |
| Symlinked/junction parent | Leaf-link removal is safe; a real leaf is deleted at its resolved physical location. Both outcomes reproduced. | Same ancestor-resolution distinction. The patch is not an ancestor containment fence. See the pre-existing hazard above. |

**Why the Windows branch is right:** Rust's Windows file type treats name-surrogate reparse points as links, including junctions; `is_symlink_dir` combines that flag with the entry's directory attribute. Rust `rmdir` calls `RemoveDirectoryW`. Microsoft's documented junction behavior explicitly removes the junction without affecting the target, even when the target is nonempty. Sources:

- https://doc.rust-lang.org/std/os/windows/fs/trait.FileTypeExt.html
- https://github.com/rust-lang/rust/blob/stable/library/std/src/sys/fs/windows.rs
- https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-removedirectoryw

**Sensitivity:** the direct junction removal, dangling junction, Delete/Disable settlement, and overwrite tests would fail on the old `remove_file` implementation. Their intact-central assertions include both `SKILL.md` and a nested script with exact bytes; a genuinely referent-traversing delete would fail them. A mutation to Rust's `remove_dir_all(link)` is not necessarily a referent-traversing delete—std itself protects leaf links—so do not use that as a misleading negative control. No Windows mutation run was performed by this reviewer.

**Limits:** add native Windows file-link and dangling symlink tests to complete the requested dynamic matrix. Also, calling `try_junction` directly forces creation of a junction but does not prove the hybrid fallback returns `SyncMode::Junction` after a forced first-leg failure; the row fixture supplies that mode itself. The unchanged fallback code at `sync_engine.rs:112–151` does have the correct symlink → junction → copy ordering. No claim of race-free safety against external filesystem replacement is made.

**Call-site rule verified:** AST call search found calls outside test files only at `artifact_removal.rs:600,761`, `onboarding_import.rs:720,748`, and `sync_engine.rs:198,240` (the latter copy seam is test-only on Unix). Import pairs removal with `ensure_path_within_tool_dirs`. No project operation or command acquired a new direct removal call.

## Opinion: pin `core.autocrlf=false` in 1.3.2

**Yes.** This is a small, evidence-backed acquisition correction, preferable to permanently disabling five good Windows tests. Skills Hub is installing managed bytes, not providing an interactive developer checkout where the machine's text-editor preference should control library content. Pin it in the application, **not** just in CI or the user's global Git configuration.

Requirements for a complete small fix:

1. CLI overrides cover clone, checkout/reset, sparse creation/widening and reuse. Do not rely only on `git clone --config` for brand-new clones while leaving existing cache entries ambient.
2. libgit2 gets the equivalent repository configuration before the initial checkout and subsequent `checkout_tree`. A CLI-only change leaves the no-system-Git path nondeterministic.
3. Existing cached CRLF worktrees need an explicit policy transition. `git_cache.rs:203–215` can return a fresh cached checkout without invoking Git at all. Merely adding a flag will not repair those bytes. Use a checkout-policy cache version/namespace or safely rebuild affected cache entries; do not casually delete the operator's central library. A cache-policy marker should distinguish old entries from already-normalized entries.
4. Test both transports under an ambient `core.autocrlf=true`, with nested/sparse acquisition and cache reuse, comparing installed bytes and content identity. Restore the five Windows tests.
5. Be precise about the guarantee: `core.autocrlf=false` removes the **ambient autocrlf** transformation. Repository-authored `.gitattributes` (`eol=crlf`, filters, etc.) can still transform checkout bytes. If the desired contract is byte-for-byte Git-blob/API equivalence for every repository, that needs an explicit attribute/filter policy or blob-based materialization—not a claim that this one switch solves every case.

The SQLite concurrency policy and full alias-aware relocation/removal redesign are separate work. Neither is a reason to abandon the targeted byte-policy fix or to re-enable launch relocation.

### R1 — P1: new cache deletion is not physically confined; a symlinked ancestor can redirect it outside the cache

**Locations:** `src-tauri/src/core/git_cache.rs:192–196, 217–235, 369–379` (especially `remove_dir_all` at `:232`).

**What is proved safe:** `repo_cache_key` hashes URL/ref to a nonempty, 64-character lowercase hexadecimal SHA-256 component (`:342–365`). Neither a URL, a branch, nor a subpath can inject `/`, `..`, an absolute path or an empty key. `prepare_repo_dir` appends the literal `skills-hub-git-cache` and that component. No direct `central_dir` value is used. With a trusted, non-aliased cache root, the leaf selected for deletion is exactly one cache entry, never the whole cache or the central root.

**What is not safe:** `create_dir_all` does not reject an existing directory symlink/junction; `clone_present` follows path resolution and merely tests whether `.git` exists. There is no physical admission check or protected-library comparison. A concrete counterexample to the requested universal guarantee is:

```text
cache/skills-hub-git-cache -> outside/
outside/<computed-key>/.git/       # a real directory, not a leaf link
outside/<computed-key>/keep       # user data; no readable policy record
```

`prepare_repo_dir(cache, key)` succeeds; `clone_present` is true; the new branch calls `remove_dir_all(cache/skills-hub-git-cache/<key>)`, deleting the **real outside directory** through its aliased parent. Making the parent of a configured central-library directory that `outside/`, with its basename equal to the computed key and `.git` present, gives the same counterexample for central. This requires a matching on-disk arrangement; it is **not** a claim that an ordinary default `~/.skillshub` is selected, or that a repository URL alone can choose an arbitrary deletion path. A symlink at the **entry leaf** is a different case: Rust removes that link itself rather than recursively following its referent. That protection does not apply to the parent alias above.

An empty or relative `cache_dir` is also accepted: the result is relative to the process working directory, not rejected or bound to an absolute admitted root. It still has the literal cache suffix and hash, so it cannot lexically collapse to `.` or `/`, but there is no API-level proof of physical ownership. Production resolves an app-cache path at the command seam (`commands/mod.rs:115–118`); that removes user URL control over the root, not filesystem aliasing of that root or its descendants.

**New versus old:** the error-retry branch already used the same deletion primitive (`git_cache.rs:306–308`). This patch newly reaches it for an otherwise healthy, fresh pre-policy clone, without any fetch failure. Do not wave this new destructive admission through as only the already-deferred target-removal problem in #88. This is a static path-resolution counterexample, not a fresh destructive reproduction against operator data.

**Smallest bounded fix:** avoid destructive migration altogether: give the new checkout policy a versioned cache namespace/key and acquire the new entry without deleting the old one. Leave old-entry reclamation to the separately admitted cleanup policy. If retaining deletion, add a physical ownership/protected-root admission contract before it (reject relative/empty roots and untrusted aliases; lexical `starts_with` or simply canonicalizing and deleting the result is insufficient). Add temp-root regressions for aliased cache parents, entry-leaf links, and invalid roots, asserting all outside/library bytes remain intact. ### R2 — P1: failed metadata persistence can cause a new delete/reclone while another acquisition copies from that entry

**Locations:** `src-tauri/src/core/git_cache.rs:198–199, 313–324, 404–413`; `src-tauri/src/core/git_acquisition.rs:404–438`; `src-tauri/src/core/sync_engine.rs:507–535`.

**The implementer's caveat is real: copy-out is after the per-key lock, not under it.** `fetch_through_cache` owns a local `_guard` and returns only `(PathBuf, String)`. The guard drops on return. `clone_path` subsequently resolves the subpath, follows upstream aliases and calls `copy_dir_recursive`; no cache guard or read lease spans those operations. Refresh can acquire several skills of the same repository concurrently.

Concrete sequence, with an unchanged upstream commit:

1. Worker A rebuilds an old entry under the new policy. Its `.skills-hub-cache.json` write fails or leaves an unreadable record; `write_meta` only logs. A is nevertheless returned the path and revision, releasing the lock.
2. A starts copying its skill from that path. Worker B takes the same key lock, reads no usable/current marker, and the new branch removes the entire entry before re-cloning.
3. A can observe a missing source/subpath or a failed directory/file read and fail an Update. If traversal overlaps deletion and repopulation, no snapshot contract guarantees a complete, single-revision copy either. A concrete failed Update is sufficient for P1; I do not claim a reproduced silent corrupt installation.

A failed write does **not always** trigger this: if an older **current-policy** record remains intact, its policy is still accepted. The bad cases are a first write after rebuilding, a missing/truncated record, or another unparseable record. Nor is this exclusively a disk-full edge case: a full cloned repository can itself contain a directory called `.skills-hub-cache.json`, making this sidecar write fail deterministically. No reservation check forbids that name here.

**New versus old:** copy-out already lacked isolation from a stale in-place refresh, and an old fetch-error retry could already remove an entry. Those are real pre-existing limitations. But a missing record previously caused an in-place fetch; against an unchanged upstream and unchanged full checkout it did not unconditionally remove every source file. The new path expands a theoretical/stale/error race to successful same-head acquisitions following a nonfatal metadata failure. It is not acceptable to dismiss that expansion as “the old code could race too.”

**Smallest bounded fix:** never hand a caller an entry whose current-policy ownership/record has not been established durably. Make a missing/invalid current-policy record-write failure fatal before returning the path, rather than warning and serving it; preserve the existing intact-current-record case only if explicitly safe. Combined with R1's non-destructive versioned migration, this prevents the newly introduced failure sequence without redesigning all acquisition. The stronger long-term fix is an entry lease/snapshot or a cache-owned copy-out operation, so every mutation/rebuild waits for readers. Do not expose a mutex and blindly hold it across `follow_upstream_links`: that code re-enters the same cache and the lock is non-reentrant. Add a deterministic two-worker regression with blocked copy-out and injected initial marker-write failure; no served path may be deleted beneath a reader.
