# 02 — Skill-level health persists on the skill row; failed first sync records an `error` row; declined records `disabled`

Status: implemented
Blocked by: 01
Spec: `.scratch/round19/spec.md` — D9 (grill Q7). Feeds #49 (issues banner + chip) and the inspector ladder.

## Why

A skill whose fetch failed, whose Edit conflicts, whose first sync was declined or failed, or whose Delete was kept
looks identical to a healthy one after the toast closes (`flows.md` X1, `critique-opus` P0-2, round-18 bake-off
finding (b)). Round 19's rows, chip, banner and ladder need stored data.

## Work

- **Schema** (additive, `skill_store` migration list): `skills.last_outcome_kind TEXT NULL`,
  `skills.last_outcome_error TEXT NULL` (the `CommandError` serialised as JSON — the same tagged shape that crosses
  the wire), `skills.last_outcome_at INTEGER NULL`.
- **Kinds** (`core/skill_health.rs`, declared in `core/mod.rs`): `SkillOutcomeKind::{FetchFailed, EditConflict,
  DeleteIncomplete, RepointFailed, RestoreFailed, ImportFailed}` — an enum with serde + `specta::Type`. One writer
  API: `record_outcome(store, skill_id, kind, &CommandError)` and `clear_outcome(store, skill_id, family)`, where a
  *family* is the set of kinds a success clears (an Update success clears `FetchFailed`/`RepointFailed`/`RestoreFailed`;
  an Edit save clears `EditConflict`; a completed Delete removes the row anyway).
- **Writers, at settlement** (where the row's `last_error` is already written today): `skill_update::apply_unlocked`
  (acquisition failure → `FetchFailed`; Edit replay conflict → `EditConflict`), `repoint.rs`, the Restore path,
  `artifact_removal` for a kept Delete (`DeleteIncomplete`), `onboarding_import` for a group that finalised but
  failed later (`ImportFailed`). Core writes it where the outcome settles — never in `commands/`.
- **Failed first sync records a target row** in `global_sync.rs`: today only `Synced` targets are recorded; a target
  that failed to materialise (any error other than `TARGET_EXISTS`) is recorded with status `error` and `last_error`,
  so the strip can render × and Retry has a row (symmetric with ADR-0002). A **declined** `TARGET_EXISTS` (the
  operator kept the existing folder) is recorded as **`disabled`** for that pair (ticket 01's grain) — the command
  seam gets the decline list from the frontend's ask (extend `sync_skills_to_tools`'s per-pair `overrides` with a
  `Keep` value beside `Overwrite`; the retry batch carries both).
- **Wire.** `ManagedSkill.health: SkillHealthDto | null` = `{ kind, error: CommandError, at }`. `getManagedSkills`
  and every `{ report, skills }` response carry it. Regenerate bindings; re-export through the shims.
- **Frontend minimum**: `skillPresentation.ts` gains a pure `skillHealth(skill)` stub returning the stored outcome
  (the full fold with severity + source line is ticket 09); `SkillCard` shows one plain text line
  ("Update failed · 2 h ago") under the Unlocatable strip so the data is visible before ticket 11 — no new styling.
- **Fixture parity**: `failures` seeds each kind; the fixture's refresh/update/repoint/delete/import handlers write and
  clear the same way; `backend.test.ts` asserts the invariants.
- **Tests**: each writer records the right kind with the row's `CommandError`; the success family clears; a
  declined pair is `disabled`; a failed first sync is an `error` row; a `TARGET_EXISTS` first sync with no decision
  is *not* recorded (it is asked first).
- **Docs.** CONTEXT.md: *Skill health* (distinct from *target* health; the stored last outcome). CHANGELOG.

### Schema and kinds

- v11 (additive, in the fresh path and presence-guarded in the incremental path like v9/v10):
  `skills.last_outcome_kind TEXT NULL`, `last_outcome_error TEXT NULL` (the tagged `CommandError` JSON — `CommandError`
  and `GitCloneFailureKind` now derive `Deserialize`), `last_outcome_at INTEGER NULL`. Like `disabled_at`, **not**
  `SkillRecord` fields (`upsert_skill` updates named columns only, so finalize/Re-point never touch them); raw store
  methods `skill_outcome` / `skill_outcomes` / `set_skill_outcome` / `clear_skill_outcome_of`.
- `SkillOutcomeKind::{FetchFailed, EditConflict, DeleteIncomplete, RepointFailed, RestoreFailed, ImportFailed}`
  (snake_case wire). API: `record_outcome(store, id, kind, &CommandError)` / `clear_outcome(store, id, family)`;
  `OutcomeFamily::Update` = {fetch, repoint, restore}, `OutcomeFamily::Edit` = {edit_conflict}. `note_outcome` /
  `note_success` are the settlement-site wrappers: a store failure there is **logged, not raised** (health is a
  projection of report data; it must not turn a settled Update into a failed one). Read policy: an unknown stored kind
  is dropped (warn); an unparsable error reads as `OTHER { message: raw }` — health never fails the catalog.
- New wire variant `CommandError::EditConflict { baseMode, upstreamMode, overrideMode }` (`EDIT_CONFLICT`) — the typed
  error an `edit_conflict` health carries; `describeCommandError` branch + `errors.editConflict`.

### Writer sites (all at settlement, in core; none in `commands/`, none for a `?`-propagated error)

| Site | Records | Clears |
|---|---|---|
| `refresh.rs` phase-2 loop (acquisition `Err` → the report row's `CommandError`) | `fetch_failed`, or `restore_failed` when the central copy is absent, or `repoint_failed` for `UpdateIntent::Repoint` | — |
| `refresh.rs::apply_one_unlocked` (`apply_unlocked` `Err`) | same rule | — |
| `skill_update::apply_unlocked` success (`settle_health`) | `edit_conflict` when the replay reported one | Update family; plus Edit family when the Edit row no longer conflicts; a direct Edit clears the Edit family |
| `artifact_removal::execute_settling_unlocked` (Delete settlement of a `Skill` scope with a failed target) | `delete_incomplete` with the first failed target's error | a completed Delete deletes the row |
| `onboarding_import::apply_one_unlocked` (finalised, then an original `Failed`) | `import_failed` with that original's error | — |

A cancellation (`CANCELLED`) records nothing. `refresh_managed_skills_with` keeps its signature (delegates to the new
`refresh_with_intent(.., UpdateIntent)`); `repoint.rs` calls the intent version. Refused Re-point targets / URLs stay
whole-command errors and record nothing (tested). Acquisition-failure health is written under the mutation guard.

### Target rows: error / Keep / unanswered (D9 + ticket 01 handoffs)

- `global_sync`: any failed attempt other than `TARGET_EXISTS` (incl. `TOOL_NOT_WRITABLE`, still reported `Skipped`)
  records every installed Tool of the shared-dir group through `TargetTransition::FailedRecorded`: new row `error` +
  `last_error` + `synced_at NULL` (**owns nothing**), an existing row keeps id/path/mode/`synced_at` (ADR-0002). An
  unanswered `TARGET_EXISTS` records **no row** (asked first).
- `BatchOverride.decision: OverrideDecision::{Overwrite, Keep}` (wire `BatchSyncOverrideDto.decision:
  "overwrite" | "keep"`, replacing `overwrite: bool`). `Keep` never attempts the sync: the attempted Tool's pair is
  recorded `DisabledRecorded` (marker, `synced_at NULL`) and reported `Skipped { TARGET_DISABLED }`; the batch's
  Disabled gate then skips it and its shared-dir siblings on every later pass (no re-ask). Delete never takes the kept folder.
- Frontend: `syncSkillsToTools` now always retries the asked pairs — `overwrite` when confirmed, `keep` when declined.
- **Enable**: a global pair whose first sync meets a folder stays `disabled` (re-recorded as a marker after the batch;
  Enable raises no ask) — fixes ticket 01's "failed Enable leaves no row"; any other failed Enable pair is the batch's
  `error` row. Project Enable/assign/resync already kept `error` assignment rows.
- **Project collision typed**: `CommandError::from_anyhow` now recovers `sync_engine::TargetExistsError` anywhere in the
  chain → `TARGET_EXISTS { path }` (project first sync, resync, Enable, Propagation's project arm).
- **Propagation fix found by the error-row test**: a never-materialised row in symlink mode was reported
  `LinkFollowsSource` and never retried. Now "a link follows the source" only for an owner (`owns_artifact`); a non-owner
  gets a first sync (overwrite off, collision = `TARGET_EXISTS` report data) — both global and project arms. Removal and
  project resync already honoured ownership (ticket 01 F1-R1); verified by test.
- **Onboarding discovery (ticket 01 handoff) — decided yes, implemented**: `list_all_skill_target_paths` returns only
  owned rows (`synced_at IS NOT NULL`), so a foreign folder at a marker / Keep / failed-first-sync row's path is
  discoverable again (it then meets 05's managed-name rules). The name now reads narrower than it is; renaming it touches
  05's `onboarding.rs` — left for 05/21.
