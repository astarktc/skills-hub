# Skills Hub — architectural friction scan (deepening opportunities)

Repo: `~/Projects/skills-hub` · HEAD at scan time: **`943f85c`** ("chore: translate
remaining Chinese comments…"), the tail of a large refactoring epic (`ee4f826`…`943f85c`, v-next
tickets 01–18: commands/core seam restored, tagged `CommandError`, one batch sync fan-out, App.tsx
carved into per-world hooks, ts-rs DTOs, hook-level vitest). Read-only scan; no files in the repo
were modified. Vocabulary per `codebase-design`; domain terms per `CONTEXT.md`.

## Map of the territory

Three tiers, two seams.

- **`src-tauri/src/core/` (21 modules, ~7.4k non-test lines + ~5.9k test lines)** — the domain.
  `tool_adapters` (the Tool registry), `installer` (intake from local/git/GitHub), `skill_store`
  (SQLite, 47 methods), `global_sync` + `project_sync` on top of `sync_engine`, plus
  `git_fetcher`/`github_download`, `gitignore`, `onboarding`, `project_ops`, `central_repo`,
  `cache_cleanup`.
- **`src-tauri/src/commands/` (1.8k lines, 57 registered commands)** — the IPC seam. Documented as
  "wiring only": DTO conversion + `CommandError` formatting, each command wrapping sync work in
  `spawn_blocking`.
- **`src/` (~10.5k lines)** — React. `App.tsx` is a binder composing per-world hooks
  (`useStatusReporter` → `useSyncOrchestration` → `useSkillLibrary` → `useSettingsState` /
  `useExploreState` / `useAddSkillFlow`; `useProjectState` for the projects world). Hooks reach the
  backend only through `src/lib/tauri.ts::invokeTauri` — the mocked seam that makes hook tests possible.

The two seams that carry the design:

1. **The IPC seam** — typed both ways: DTOs generated by ts-rs into `src/bindings/`, errors as the
   tagged `CommandError` (ADR-0001). This seam is in good health; most findings below are about
   *what leaks across it* or *which tier owns the logic behind it*, not about the seam itself.
2. **The `invokeTauri` seam** — the frontend test surface.

The best-shaped module in the repo is `core/global_sync.rs`: environment probing is isolated in
`plan_batch_tool_targets` (global_sync.rs:326–356) so the deterministic engine
`sync_skills_to_planned_tools` (global_sync.rs:363–458) can be driven by tests with fabricated roots
(`core/tests/global_sync.rs:316` `fn planned(...)`, 678 test lines). **Several findings below are
"apply the `global_sync` pattern to the place that didn't get it yet."**

Where the epic did *not* reach: `tool_adapters` path resolution, the project-scope counterpart of the
batch engine, the settings surface, and `installer`'s intake tail.

## Findings

### 1. Skill deletion and project fan-out choreography live in the command tier, unreachable by tests

**Files** `src-tauri/src/commands/mod.rs`, `src-tauri/src/commands/projects.rs`,
`src-tauri/src/core/project_ops.rs`

**Problem** AGENTS.md states `commands/` is wiring only and `core/` holds independently testable
business logic. Three of the app's most destructive/most branching operations violate that: their
*implementation* sits inside a `#[tauri::command]`, so the module's interface is an IPC command and
its only possible test surface is a running Tauri app. There is no seam to test through, and no test
exists. `core/project_ops.rs` already establishes the counter-pattern (`remove_tool_with_cleanup`,
`remove_project_with_cleanup`), which makes skill deletion the odd one out rather than a convention.

**Evidence**
- `commands/mod.rs:986–1053` `delete_managed_skill`: 60 lines of cross-world logic — global target
  removal (998–1004), *project* artifact removal (1006–1031), central-dir removal + cascade
  (1033–1039), typed `DeleteCleanupFailed` (1041–1046). It re-implements the project target join by
  hand at 1019–1023 instead of calling `project_sync::resolve_project_sync_target`, and re-implements
  the status filter with string literals at 1010–1012.
- `commands/projects.rs:346–413` `bulk_assign_skill`: the project-scope fan-out — project/skill
  lookup, already-assigned dedupe (377–382), per-tool failure isolation into `BulkAssignErrorDto`
  (399–405). This is precisely the shape `global_sync::sync_skills_to_planned_tools`
  (`global_sync.rs:363–458`) has in core, where it is covered by 15 tests.
- `commands/projects.rs:417–456` `update_project_gitignore`: project lookup, `is_dir` validation,
  tool→adapter mapping and pattern derivation (439–444) — composition logic above a well-tested
  `core/gitignore.rs` (317 test lines), itself untested.
- Test-coverage asymmetry: `src-tauri/src/commands/tests/commands.rs` is 277 lines and tests only
  `CommandError::from_anyhow` and `expand_home_path`. Nothing above is reachable.

**Proposed deepening** Move each body into `core/` behind one narrow call: a
`core/skill_removal.rs` (or `installer::remove_managed_skill`) that takes `(&SkillStore, skill_id)`
and returns a removal report; a `project_sync::assign_skill_to_project_tools(...)` mirroring
`sync_skills_to_planned_tools` (probe → deterministic engine → per-target status); and a
`gitignore::update_for_project(&store, project_id, options)`. The commands become the 3-line
DTO-conversion wrappers the invariant promises.

**Benefits** *Locality*: the "what happens to files when a skill/tool/project goes away" rule lives
in one module instead of being split between `commands/mod.rs`, `commands/projects.rs`, and
`project_ops.rs`. *Leverage*: the same engine serves `bulk_assign`, `add_project_skill_assignment`
and `resync_project`. *Tests*: the deterministic halves become table-testable with temp dirs, exactly
as `core/tests/global_sync.rs` already does — and the tests can assert typed statuses instead of
nothing.

**Strength** Strong

**ADR/invariant conflicts** None — this *restores* the documented `commands/`-is-wiring invariant
(`ee4f826` "restore the commands/core seam" started this work; these three are the remainder).

### 2. `resolve_project_sync_target` makes the caller choose between two dir mappings — and one caller chooses wrong

**Files** `src-tauri/src/core/project_sync.rs`, `src-tauri/src/core/project_ops.rs`,
`src-tauri/src/core/tool_adapters/mod.rs`, `src-tauri/src/commands/mod.rs`

**Problem** Each Tool has *two* skills-dir facts: `ToolAdapter.relative_skills_dir` (global, under
`$HOME`) and `project_relative_skills_dir(adapter)` (project scope). The interface of
`resolve_project_sync_target(project_path, relative_skills_dir: &str, skill_name)` accepts a bare
`&str`, so "which of the two mappings applies in project scope" is knowledge pushed onto every
caller. That is a shallow interface hiding nothing: it is one `join`, and its parameter is the
mistake surface. The mistake is already present in the tree.

**Evidence**
- Definition: `project_sync.rs:13–19` (three params, body is `project_path.join(dir).join(name)`).
- Five call sites pass the project mapping: `project_sync.rs:49`, `:121`, `:251`, `:367`,
  `installer.rs:939` — all `project_relative_skills_dir(&adapter)`.
- One passes the **global** mapping: `project_ops.rs:138` `adapter.relative_skills_dir`, inside
  `remove_tool_with_cleanup`'s orphaned-assignment cleanup. For every tool whose two mappings differ
  (`tool_adapters/mod.rs:482–528`: Cursor `.cursor/skills` vs `.agents/skills`; Pi `.pi/agent/skills`
  vs `.pi/skills`; Codex, Goose, Augment, Windsurf, OpenClaw…) this computes a path that project sync
  never wrote, so the orphan is left on disk.
- A sixth site bypasses the helper entirely and hand-joins: `commands/mod.rs:1019–1023`.
- This exact class of bug is documented as already-fixed elsewhere: `core/gitignore.rs:1–13` — "An
  earlier version derived patterns from the *global* `relative_skills_dir`, producing entries that
  never matched what project sync actually wrote for tools like Windsurf/Pi/Goose/Augment."

**Proposed deepening** Change the interface to take the adapter, not a string:
`resolve_project_sync_target(project_path, &ToolAdapter, skill_name)`, choosing the project mapping
inside. Delete the `&str` parameter so the wrong mapping is unrepresentable, and route
`commands/mod.rs:1019` through it.

**Benefits** *Locality*: the project-scope dir decision is made once, in the same spirit
`gitignore.rs` already documents for patterns. *Leverage*: six call sites get shorter and
mechanically correct. *Tests*: one test per tool-with-divergent-mapping pins the behaviour for all
callers instead of each caller needing its own.

**Strength** Strong (smallest change of any finding here; fixes a live defect)

**ADR/invariant conflicts** None.

### 3. Tool detection and global path resolution have no home-root seam, so the newest engine's probing half is untestable

**Files** `src-tauri/src/core/tool_adapters/mod.rs`, `src-tauri/src/core/onboarding.rs`,
`src-tauri/src/core/global_sync.rs`, `src-tauri/src/commands/mod.rs`,
`src-tauri/src/core/central_repo.rs`, `src-tauri/src/core/skill_lock.rs`

**Problem** `resolve_default_path`, `resolve_detect_path` and `is_tool_installed` create their
dependency instead of accepting it — each calls `dirs::home_dir()` internally. The module's interface
therefore contains an invisible required fact ("this reads the operator's real `$HOME`"), which makes
every module composed on top untestable and forces callers who *do* want a fake home to bypass the
functions and re-implement the join. The precedent for the fix already exists one module over.

**Evidence**
- `tool_adapters/mod.rs:536–548`: `resolve_default_path` / `resolve_detect_path` / `is_tool_installed`
  each resolve `dirs::home_dir()` inline.
- `core/tests/tool_adapters.rs` (83 lines) tests only `adapter_by_key`, `adapters_sharing_skills_dir`
  and `scan_tool_dir` — the three functions that don't touch `$HOME`. Installedness and path
  resolution have zero tests.
- Consequence in the newest code: `global_sync::plan_batch_tool_targets` (global_sync.rs:326–356)
  and the composed `sync_skills_to_tools` (global_sync.rs:464–502) are the *only* untested functions
  in an otherwise exhaustively tested module (`core/tests/global_sync.rs`, 678 lines) — precisely
  because they call `is_tool_installed` / `resolve_default_path`.
- Consequence in `commands/`: `get_tool_status` (commands/mod.rs:68–130) and
  `get_project_tool_status` (:133–207) can never be tested.
- The precedent: `onboarding.rs:40–54` `build_onboarding_plan` resolves `dirs::home_dir()` and
  immediately delegates to `build_onboarding_plan_in_home(home: &Path, …)` (`:56`), which
  `core/tests/onboarding.rs` drives against three temp homes. But because
  `resolve_default_path`/`resolve_detect_path` are unusable with a fake home, that function
  re-implements them by hand at `onboarding.rs:66` and `:70`.
- Same shape for the *other* path fact: `expand_home_path` lives in the wiring tier
  (`commands/mod.rs:286–300`) and is injected into core as a closure parameter
  (`project_ops.rs:82`, `:251`), so core depends on `commands`. One production adapter, one
  hand-written fake — and the fake has diverged: `core/tests/project_ops.rs:16` `test_expand_home`
  bails `"path is empty"` where production bails `"storage path is empty"`
  (`commands/tests/commands.rs:137–138` asserts the latter, against the machine's real `$HOME` at
  `:130`).

**Proposed deepening** Introduce one home-root parameter in `tool_adapters`
(`skills_dir_in(home, adapter)`, `detect_dir_in(home, adapter)`, `is_installed_in(home, adapter)`),
keep thin `dirs::home_dir()`-resolving wrappers for production, and thread the root through
`plan_batch_tool_targets`. Move `expand_home_path` into `core/` next to them and delete the injected
closure from `register_project_path`/`update_project_path` (one adapter is a hypothetical seam; this
one exists only because the function is in the wrong tier).

**Benefits** *Leverage*: one seam serves tool status, batch planning, onboarding, `skill_lock`, and
central-repo defaulting. *Locality*: `onboarding.rs` stops duplicating the joins. *Tests*: the last
untested function in `global_sync`, plus both tool-status assemblers, become temp-dir testable — and
the divergent test fake gets deleted rather than maintained.

**Strength** Strong

**ADR/invariant conflicts** None.

### 4. Sync status is a stringly-typed lifecycle spread across five modules and three DTOs

**Files** `src-tauri/src/core/skill_store.rs`, `src-tauri/src/core/project_sync.rs`,
`src-tauri/src/core/project_ops.rs`, `src-tauri/src/core/installer.rs`,
`src-tauri/src/commands/mod.rs`, `src/bindings/*.ts`,
`src/components/projects/AssignmentMatrix.tsx`

**Problem** ADR-0001 replaced stringly-typed *errors* with a tagged enum checked by both compilers.
The parallel concept — a Sync target's / assignment's lifecycle (`pending` → `synced` / `stale` /
`missing` / `error`, plus mode `symlink`/`copy`) — is still raw strings. No module owns the state
machine: transitions are written by four modules, aggregated by a fifth, and re-derived by the
frontend. The write interface is maximally shallow: `update_assignment_status(&self, id, status: &str,
last_error: Option<&str>, synced_at: Option<i64>, mode: Option<&str>, content_hash: Option<&str>)` —
six positional params whose legal combinations are unwritten, called nine times with three or four
`None`s.

**Evidence**
- Interface: `skill_store.rs:858–866`. Callers: 9 in `project_sync.rs`/`installer.rs`
  (e.g. `project_sync.rs:266–276`, `:287–297`, `:319–330`, `:336–345`).
- Transition sites in four modules: `project_sync.rs:38` (`"pending"`), `:69`, `:84`, `:147`, `:176`;
  `installer.rs:946`, `:958`, plus `"ok"` for skill targets at `installer.rs:104`, `:201`, `:883`,
  `:908`, `:1393` and `global_sync.rs:145`.
- Aggregation by string match: `skill_store.rs:993–1035`, the match at `:1013–1019`
  (`"error" | "missing" => has_error`, …), returning another bare `String`.
- Read-side duplication of the same literals: `project_ops.rs:185`, `commands/mod.rs:1010–1012`.
- Wire: `src/bindings/ProjectSkillAssignmentDto.ts`, `SkillTargetDto.ts`, `ManagedSkillDto.ts` all
  carry `status: string` (and `ProjectDto.sync_status: String`, `project_ops.rs:24`) — while the
  *newer* `SyncTargetStatusDto.ts` is a properly tagged union. The frontend turns the untyped one
  straight into a CSS class: `AssignmentMatrix.tsx:419–424`.
- The staleness recomputation reads environment, decides, and writes the DB in one loop
  (`project_sync.rs:217–354`), so there is no pure decision function to test — the opposite of
  `global_sync`'s plan/execute split.

**Proposed deepening** Introduce one `SyncStatus` (and `SyncMode`) enum in core with a
`#[ts(export)]` derive, exactly as ADR-0001 did for errors, and give the assignment lifecycle a
module: a pure `next_status(observation) -> SyncStatus` (source present? target present? mode? hashes?)
plus a `reconcile` step that applies transitions. Replace the six-param setter with a small typed
transition call.

**Benefits** *Locality*: the state machine becomes one readable function instead of four scattered
literal sites. *Leverage*: the frontend gets exhaustiveness checking for free, the same way
`commandError.ts`'s `satisfies Record<CommandError["code"], true>` guards error codes today. *Tests*:
the decision half becomes a pure table test (no temp dirs, no DB), which is where the D-04/D-05/D-07
rules encoded in `project_sync.rs` comments actually deserve coverage.

**ADR/invariant conflicts** None — this extends ADR-0001's reasoning to the second stringly-typed
wire field rather than contradicting it.

**Strength** Strong

### 5. The central-repo intake tail is copy-pasted across four install entry points, and the copies have diverged

**Files** `src-tauri/src/core/installer.rs`

**Problem** "Materialise a skill into the central repo and record it" is a real domain operation with
no module. Instead, four entry points each hand-roll it: name derivation, the already-exists check,
`SKILL.md`-preferred renaming, description extraction, content hashing, and a 14-field `SkillRecord`
literal. Nothing is behind an interface, so the rules can only be verified once per entry point —
and the copies have drifted.

**Evidence**
- The same 14-field `SkillRecord` literal with `status: "ok"` and `created_at/updated_at/last_seen_at
  = now` appears at `installer.rs:90–105` (`install_local_skill`), `:187–202` (`install_git_skill`),
  and `:1379–1394` (`install_git_skill_from_selection`).
- The exists-check is duplicated as prose three times: `installer.rs:61`, `:147`, `:1324`
  (`bail!("skill already exists in central repo: {:?}")`).
- Divergent copies of the rename block: in `install_git_skill` the description re-read sits **outside**
  the `if !new_central.exists()` guard (`installer.rs:176–179`, guard closes at `:175`); in
  `install_git_skill_from_selection` the same three lines sit **inside** it
  (`installer.rs:1364–1366`, guard `:1358–1367`). Same intent, two shapes — the signature of
  copy-paste rather than a decision.
- The prose leaks across both seams: `src/commandError.ts:65–76` string-matches
  `"skill already exists in central repo"` and reverse-engineers the skill name out of the message,
  and `core/tests/installer.rs:218` asserts `format!("{:#}", err).contains("skill already exists")` —
  the test surface itself crosses on prose.

**Proposed deepening** One `installer` (or `central_repo`) entry: `record_new_skill(store,
central_dir, staged_dir, NameIntent) -> Result<InstallResult>` owning the exists-check (as a typed
`SignalError::SkillExists { name }`), the `SKILL.md`-preferred rename, description, hash, and the
record. The four entry points shrink to "acquire bytes into a staging dir, then call it."

**Benefits** *Locality*: one place to change what an installed Managed skill's record looks like —
today a new field means four edits. *Leverage*: the fifth entry point (explore one-click install)
comes free. *Tests*: the rename/description/hash rules get one test each instead of being retested
per path, and the exists case becomes a typed assertion, letting `describeCommandError`'s
`describeOther` string-matching branch be deleted — which ADR-0001 explicitly names as the smell
signalling "a typed variant is due."

**Strength** Strong

**ADR/invariant conflicts** None (ADR-aligned).

### 6. The settings surface is 14 commands with no module, and its bounds are duplicated across the IPC seam

**Files** `src-tauri/src/commands/mod.rs`, `src-tauri/src/core/cache_cleanup.rs`,
`src-tauri/src/core/skill_store.rs`, `src/hooks/useSettingsState.ts`, `src-tauri/src/lib.rs`

**Problem** The only settings interface is `SkillStore::get_setting(&str) -> Option<String>` /
`set_setting(&str, &str)` — maximally generic, so every caller re-implements key naming, parsing,
defaulting and clamping. Those callers then need one `#[tauri::command]` pair each, and the frontend
needs one `useEffect` each. 14 of the 57 registered commands (~25%) are settings accessors whose
bodies are two lines. Deletion test: delete any one of these command pairs and complexity does *not*
reappear elsewhere — they are pass-throughs; the real logic that *would* reappear (parse + default +
clamp) is the part that has no home.

**Evidence**
- Interface: `skill_store.rs:271–291`. Callers with hand-rolled parse/default:
  `commands/mod.rs:104` (`installed_tools_v1` via `serde_json`), `:733` (`auto_sync_enabled`),
  `:768–771` (`global_selected_tools_v1`, `scan_selected_tools_only`), `:829` (`ui_zoom_level`),
  `cache_cleanup.rs:24–53`, `central_repo.rs:15`, `featured_skills.rs:52–58`,
  `installer.rs:1649`, and again in `lib.rs:44` for the pre-paint zoom read.
- Command pairs: `lib.rs` `generate_handler!` registers get/set for `central_repo_path`,
  `git_cache_cleanup_days`, `git_cache_ttl_secs`, `github_token`, `auto_sync_enabled`,
  `global_tool_config`, `ui_zoom_level` — 14 entries; their bodies are
  `commands/mod.rs:222–275`, `:303–375`, `:698–755`, `:797–852`.
- Bounds duplicated across the seam, as literals: `useSettingsState.ts:173`
  `Math.max(0, Math.min(nextDays, 3650))` vs `cache_cleanup.rs:14`
  `MAX_GIT_CACHE_CLEANUP_DAYS: i64 = 3650`; `useSettingsState.ts:193` `Math.min(nextSecs, 3600)` vs
  `cache_cleanup.rs:17` `MAX_GIT_CACHE_TTL_SECS = 3600`. Neither side knows the other exists.
- Frontend cost: `useSettingsState.ts` holds 9 `useEffect`s and 13 `invokeTauri` calls, five of them
  one-shot mount loads of a single scalar (`:79`, `:87`, `:95`, `:103`, `:110`).

**Proposed deepening** A `core/settings.rs` owning typed keys: one enum/struct of known settings with
per-setting parse, default and bound, plus `get_settings(&store) -> AppSettings` and
`set_setting(&store, Setting)`. Two commands replace fourteen; the frontend's five mount effects
collapse to one, and the clamp bounds ship in the DTO instead of being retyped in TypeScript.

**Benefits** *Locality*: adding a setting is one enum arm, not (const + 2 core fns + 2 commands +
1 handler registration + 1 effect + 1 handler). *Leverage*: validation is written once and both
tiers obey it. *Tests*: parse/default/clamp becomes a pure table test in core (today
`core/tests/skill_store.rs:45–49` can only assert that a string round-trips), and the frontend hook
test needs one mocked command instead of five.

**Strength** Strong

**ADR/invariant conflicts** None.

### 7. The GitHub HTTP layer drops the status code into prose, and the installer sniffs it back out

**Files** `src-tauri/src/core/github_download.rs`, `src-tauri/src/core/installer.rs`

**Problem** A typed condition is available at the origin and deliberately discarded, forcing the
consumer 1500 lines away to reconstruct it by substring match. This is the exact failure mode
ADR-0001 was written to end, surviving at one seam — and the code comment admits it.

**Evidence**
- `github_download.rs:136–168` `check_github_response` holds `let status = resp.status();` (`:140`),
  raises a typed `SignalError::RateLimited` only when the `x-ratelimit-reset` header parses
  (`:158`), and otherwise throws the code away: `bail!("403 Forbidden")` (`:159`) and
  `anyhow!("GitHub API error {} for: {}", status, context)` (`:165–168`).
- `installer.rs:1695` and `:1705` then re-derive it: `if err_msg.contains("404") ||
  err_msg.contains("Not Found")` → `SignalError::GithubSkillNotFound`; `if err_msg.contains("403")
  || err_msg.contains("Forbidden")` → `SignalError::RateLimited { reset_minutes: 0 }`. The comment at
  `:1690–1693` states the reason: "the GitHub HTTP layer currently surfaces status codes only as
  strings in the error chain, so we sniff 404/403 here."
- The fix is cheap because the module is already test-shaped: `github_download.rs:297–375` tests
  `check_github_response` against a mock server for success, 403-with-reset, 403-without-reset and
  other errors.

**Proposed deepening** Give `check_github_response` a typed error carrying the status (a
`GithubHttpError { status, reset_minutes: Option<i64> }`, or two more `SignalError` arms), and have
`installer::fetch_skill_files` match by downcast. Delete both `contains(...)` branches.

**Benefits** *Locality*: HTTP-status classification happens once, where the response object lives.
*Leverage*: every future GitHub caller (e.g. `fetch_branch_sha`, `github_download.rs:207–245`)
inherits the classification. *Tests*: the existing mock-server tests can assert the variant instead
of a message, and the 404 path — currently only reachable through a real network error string — gets
its first test.

**Strength** Strong

**ADR/invariant conflicts** None; ADR-0001-aligned (its "Considered options" already rejected
frontend-side classification for exactly this reason: "the backend has the full error chain; it
classifies").

### 8. The Tool concept is split across four places, and its module carries dead interface

**Files** `src-tauri/src/core/tool_adapters/mod.rs`, `src-tauri/src/commands/mod.rs`,
`src-tauri/src/core/skill_store.rs`

**Problem** `CONTEXT.md` names Tool, Virtual group, Constituent tools and Shared skills dir group as
backend-owned domain concepts. In code, one Tool's facts are spread over four locations that must be
edited in lockstep, only two of which the compiler checks — and the presentation of the whole catalog
(which entries exist, which are installed, which are absorbed into the virtual group) lives in two
near-duplicate command bodies rather than in the module that owns the concept.

**Evidence**
- Fact 1–4 of a Tool: the `ToolAdapter` literal (`tool_adapters/mod.rs:138–453`, 44 entries; struct
  at `:119–127`); the project-scope dir in a *separate* match on `ToolId`
  (`:482–528`); virtual-group membership as a list of nine **string keys** duplicating `ToolId`
  variants (`:6–16` `AGENTS_STANDARD_KEYS`); plus a README table AGENTS.md flags as unenforced.
- The catalog assembly lives in commands and is duplicated: `get_tool_status`
  (`commands/mod.rs:68–130`) and `get_project_tool_status` (`:133–207`) both build `Vec<ToolInfoDto>`
  + `installed`, diverging on virtual-group absorption and `shared_with`. The literal
  `"agents_skills"` is rewritten four times (`:165`, `:172`, `:176`, and the key comparison at
  `:143`) even though `ToolId::AgentsStandard.as_key()` returns exactly that (`:70`).
- `get_tool_status` also silently owns a side effect — persisting `installed_tools_v1` and diffing
  `newly_installed` (`:104–120`) — inside a getter.
- Cost per lookup: `adapter_by_key` (`:530`) and `adapters_sharing_skills_dir` (`:456`) each rebuild
  all 44 adapters by value; the latter is called inside the 44-iteration loop at `:82`.
- Dead interface: `adapters_sharing_project_skills_dir` (`:463`), `resolve_project_path` (`:472`) and
  `supports_project_scope` (`:477`) are all `#[allow(dead_code)]` — deleting them removes complexity
  and nothing reappears (16 such markers exist across `core/`).
- The same virtual-group consolidation is re-encoded a third time as a SQL migration
  (`skill_store.rs:231–247`).

**Proposed deepening** Make `ToolAdapter` hold every per-tool fact (add `project_relative_skills_dir`
and a `group: Option<VirtualGroup>` field) so the struct literal is the single record per tool and
the compiler enforces completeness; expose the catalog as two functions in `tool_adapters` —
`global_tool_entries(home)` and `project_tool_entries()` — returning presentation-ready entries with
`shared_with`/`constituents` resolved. `get_tool_status` becomes a DTO map plus an explicit
`record_installed_tools` call. Drop the three dead functions.

**Benefits** *Locality*: adding a Tool becomes one struct literal instead of "vec entry + match arm +
maybe a string list + README". *Leverage*: both scopes and `gitignore`/`project_sync` read one
mapping. *Tests*: with finding 3's home seam in place, the whole catalog (virtual-group absorption,
shared-dir grouping, installedness) becomes testable against a temp home — today it has no test at all.

**Strength** Strong

**ADR/invariant conflicts** Touches the AGENTS.md "New AI tool adapter" invariant — it would make
that invariant *smaller* (one struct literal + README row) rather than contradicting it; the
invariant text needs updating in the same pass.

### 9. `useAddSkillFlow` exposes 44 members, and its git/local candidate picking is a mirrored pair with divergent validation

**Files** `src/hooks/useAddSkillFlow.ts`, `src/components/skills/modals/GitPickModal.tsx`,
`src/components/skills/modals/LocalPickModal.tsx`

**Problem** The Add/import world's interface is 44 names for 841 lines — 12 of them raw `useState`
setters and 8 modal open/close guards whose bodies are `if (!loading) setShowX(false)`. Depth is
leverage per unit of interface learned; here the binder must learn nearly one name per 19 lines of
implementation. Inside, the git and local candidate flows are a mirrored pair rather than one module
with two adapters — and the mirror has diverged on validation, which is where the user-visible
behaviour lives.

**Evidence**
- Returned interface: the single `return { … }` at `useAddSkillFlow.ts:795` lists 44 members.
  Complexity 95 for one function.
- Mirrored member pairs: `gitCandidates`/`localCandidates`, `gitCandidateSelected`/
  `localCandidateSelected`, `showGitPickModal`/`showLocalPickModal`,
  `handleToggleAllGitCandidates` (`:255`) / `handleToggleAllLocalCandidates` (`:264`),
  `handleToggleGitCandidate` (`:275`) / `handleToggleLocalCandidate` (`:285`),
  `handleCancelGitPick` (`:217`) / `handleCancelLocalPick` (`:229`),
  `handleInstallSelectedCandidates` (`:758`) / `handleInstallSelectedLocalCandidates` (`:701`).
- Divergence in the mirror: the local path rejects duplicate names *within* the selection
  (`:713–724` — the `seen` set) and falls back to `selected[0].name` when a custom name is given for
  one item (`:725–728`); the git path (`:758–793`) has neither check, so two same-named candidates in
  one repo proceed to a mid-batch failure.
- The install→deploy tail was already deduped into `runBatchInstall` (`:655–699`, commit `f0149de`) —
  proof the seam is real; the *selection* half wasn't.
- Two adapters exist here (git source, local source), so the seam is real, not hypothetical.

**Proposed deepening** One `useCandidatePick(source)` module owning `{candidates, selected,
basePath/repoUrl, visible}` plus `validate` and `install`, parameterised by a small source adapter
(`discover`, `installOne`, `resetExtras`). It returns one object; `useAddSkillFlow` re-exports two
instances. Fold the eight `if (!loading) setShowX(false)` guards into one shared modal-visibility
helper.

**Benefits** *Locality*: the "which selections are legal" rule is written once, so the git/local
divergence cannot recur. *Leverage*: the binder learns one shape twice instead of two shapes.
*Tests*: `useAddSkillFlow.test.ts` (364 lines) currently tests the flow through the widest possible
surface; a `useCandidatePick` module is directly testable at `renderHook` level with a stub source,
and the validation rules become cheap table cases.

**Strength** Worth exploring (the interface reduction is clear; the exact split of what stays in
`useAddSkillFlow` needs a design pass)

**ADR/invariant conflicts** None — consistent with the documented per-world-hook pattern.

### 10. A backend ordering invariant is enforced by a React ref, behind a raw `invoke` that no test can reach

**Files** `src/components/projects/ProjectsPage.tsx`, `src/components/projects/EditProjectModal.tsx`,
`src-tauri/src/commands/projects.rs`

**Problem** `update_project_gitignore` derives its patterns from the project's *already-persisted*
tools, so it must run after tools are written. That ordering constraint is part of the command's
interface, and nothing in the interface says so; instead it is enforced in the deepest, least
testable place available — a `useRef` in a page component, reached through a raw `invoke` that
bypasses the `invokeTauri` seam the hook tests mock.

**Evidence**
- Backend dependency: `commands/projects.rs:439–444` — `store.list_project_tools(&projectId)` →
  `adapter_by_key` → `patterns_for_tools`.
- Frontend choreography: `pendingGitignoreRef` is declared at `ProjectsPage.tsx:25–29` (its comment
  at `:21–24` already spells out the constraint: "update_project_gitignore derives patterns from
  list_project_tools, so it MUST be called AFTER tools are persisted"); `handleAddProject`
  (`:31–59`) stashes the user's intent, and `handleToolConfigConfirm` (`:61–96`) replays it after
  tool config is confirmed, per the comment at `:73–75`.
- Seam bypass: `ProjectsPage.tsx:4` imports `invoke` directly (calls at `:80`, `:133`), as does
  `EditProjectModal.tsx:5`. Per AGENTS.md components get no JSX tests by design, so these two
  command interactions have no test path at all — while `core/gitignore.rs` itself is well covered
  (`core/tests/gitignore.rs`, 317 lines).

**Proposed deepening** Let the backend own the ordering: either have `update_project_gitignore`
accept the intended tool set (deriving patterns from the request rather than from the DB), or let the
tool-config command take an optional gitignore intent and sequence both writes in core. The ref, the
replay, and both raw `invoke` sites disappear.

**Benefits** *Locality*: the ordering rule lives next to the code that creates it, so it can't be
violated by a second caller. *Leverage*: `EditProjectModal`'s path and the add-project path stop
being two independent orderings. *Tests*: the sequencing moves into a tier that has tests
(`core/tests/gitignore.rs`), and the projects world regains full coverage through the `invokeTauri`
seam that `useProjectState` already uses for its other 23 calls.

**Strength** Worth exploring

**ADR/invariant conflicts** Sits against the documented allowance that "raw `invoke` is allowed only
in components" — this finding argues the allowance is load-bearing here in a bad way, not that the
convention is wrong in general.

## Top recommendation

**Start with finding 3 (the home-root seam), then finding 2 in the same pass.**

Finding 1 is the largest architectural prize and finding 4 the widest-reaching, but both produce
modules whose *probing* half still cannot be verified while `dirs::home_dir()` is called inside
`tool_adapters`. Finding 3 is the enabling change: it is mechanical (three functions gain a `home`
parameter, existing wrappers keep production behaviour), it has a proven in-repo precedent to copy
verbatim — `onboarding.rs:40–56` plus its temp-home tests — and it immediately converts the last
untested functions of the newest engine (`plan_batch_tool_targets`, `sync_skills_to_tools`) and both
tool-status assemblers from untestable to temp-dir testable. It also removes the duplicated joins at
`onboarding.rs:66,70` and lets the divergent `test_expand_home` fake
(`core/tests/project_ops.rs:16`) be deleted rather than maintained.

Bundle finding 2 with it because it is the cheapest defect fix in this report — replace one `&str`
parameter with `&ToolAdapter` in `resolve_project_sync_target` and the wrong-mapping bug at
`project_ops.rs:138` becomes unrepresentable, with a per-tool test to pin it.

With the seam in place, tackle finding 1 next (move `delete_managed_skill` and `bulk_assign_skill`
into `core/`, mirroring `global_sync`'s plan/execute split) — that is where the real, currently
unverifiable risk lives, and it is the finding whose tests the seam unlocks.
