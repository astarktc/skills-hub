## D1 — finalize always records the content hash (release-build Stale bug)
`install_finalize::compute_content_hash` (~469) returns `None` unless `cfg!(debug_assertions)` or `SKILLS_HUB_COMPUTE_HASH=1`. In a release build `finalize_update`/`finalize_install` record `content_hash: None`; Propagation writes that `None` into every copy-mode assignment row (`propagation.rs:~390`); the next reconcile pass hashes the source (`project_sync.rs:~503`) and `sync_status::next_status` returns `Stale` (`Some(_)` vs recorded `None`). Every copy-mode project assignment reports Stale after every Update, in shipped builds only; the suite is debug-only so it cannot see it.
→ Delete `should_compute_content_hash` and the env var; `compute_content_hash` always runs `hash_dir` and on failure logs `warn!` and returns `None` (unchanged failure shape). Remove the `SKILLS_HUB_COMPUTE_HASH` mention from the `AGENTS.md` "Core never resolves filesystem roots" bullet's sanctioned-env-var list (`install_finalize.rs` is named there; keep the other two files listed).
Tests: (a) `finalize_update` and `finalize_install` record `Some(hash)` equal to `content_hash::hash_dir` of the landed dir; (b) an end-to-end test through the real supplier: Update of a skill with a copy-mode project assignment → assignment row's `content_hash` is `Some` and equals the skill row's → a reconcile pass (`project_sync` listing/observe) reports `Synced`, not `Stale`. Do not hand-feed `Some("hash-v2")` in the new test (that is why `tests/propagation.rs:113` never caught it).

## D2 — Edit replay runs inside finalize's failure-atomic window
`finalize_update` (~272-308) moves the old central copy aside, lands bytes, upserts the row, then **removes the backup**; only afterwards does `installer::finalize_and_propagate_unlocked` (~387-391) call `skill_edits::replay_unlocked(..)?`. Replay can fail on the edit-row upsert, the manifest write (`frontmatter_edit::apply_to_file`) or `record_hash`. A replay failure therefore reports a failed Update whose central bytes are already replaced and whose recovery bytes are gone.
→ Widen finalize's window: `finalize_update` gains a step that runs **after** the row upsert and **before** the backup is released, and whose failure takes the existing `rollback_update` path (restore old bytes + re-upsert the old row — same machinery `finalize_update_restores_old_bytes_when_upsert_fails` proves). Shape is yours (a closure parameter `FnOnce(&mut SkillRecord) -> Result<T>` on `finalize_update`, or a split `land`/`settle`/`release` triple used by `finalize_and_propagate_unlocked`) — pick the one with the smaller interface; every existing caller of `finalize_update` must keep working (Restore's rebuild path included). `finalize_and_propagate_unlocked` passes replay as that step; the conflict result still comes out in `UpdateOutcome`.
Edit-row consistency on rollback: `replay_unlocked` upserts the edit row (new `base_value`, `applied_at`, `conflict`) **before** writing bytes (row-is-source-of-truth, keep that order). If the step fails after that upsert and finalize rolls the bytes back, the edit row must be restored to what replay read at entry — replay (or the step wrapper) snapshots the row and re-upserts the snapshot on its own failure; a double fault is named in the error, not swallowed. Also confirm: the skill row re-upserted by rollback is the **pre-finalize** record (incl. its old `content_hash`), not the half-settled one.
Acquire-first and the guard are untouched: no acquisition-side change, no new lock. `finalize_install` (Add) has no Edits and is unchanged.
Tests: (a) Update with a persisted invocation-mode Edit + an injected failure in replay's manifest write (or a SQLite trigger on `skill_edits` upsert, the fault seam `tests/skill_edits.rs` / round-8 S3 already use) → central bytes are the **old** bytes, skill row is the old row, edit row is the pre-Update row, no `.skills-hub-old-*` sibling left behind on the success path and one left + named on a failed rollback (existing tests); a retry Update with the fault removed succeeds and replays. (b) The happy path is byte-identical to today: `update_replays_and_clear_restores_current_upstream_bytes_and_hash` and the rest of `tests/skill_edits.rs` / `tests/refresh.rs` unchanged. (c) Restore of an Unlocatable skill (central copy gone, no backup) still works with the new step in place.
