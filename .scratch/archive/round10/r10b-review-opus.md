1. **Refused Bequest (follow-up)** — `src-tauri/src/core/git_acquisition.rs:509`. `acquire()` accepts `SkillIntent::Selection(GitSelection{subpath: None})` (the listing intent) but cannot serve it; `resolve_subpath` bails with prose *after* `fetch_repo` has already cloned. A separate listing seam type — or making `Selection`'s subpath non-optional and giving `list_candidates_with` its own intent — would remove the unserviceable variant. Ticket 03 §2 only requires "listing is `Selection` without a selected subpath", which this satisfies.
2. **Middle Man / signature coupling (follow-up)** — `src-tauri/src/commands/mod.rs:818-840`. `update_managed_skill` calls the `#[tauri::command]` `refresh_managed_skills` as a plain function and then opens a second `spawn_blocking` for the catalog. It works and correctly reuses the batch-of-one core policy (ticket 05 §2 explicitly allows this shape), but the Update path now silently inherits the batch command's `State` extraction and `cancel.reset()`, and any future parameter change to `refresh_managed_skills` rewrites this wrapper. A shared private `async fn` taking the already-cloned `store`/`cancel` would decouple them.
3. **Mysterious Name (follow-up)** — `src/hooks/useSkillLibrary.ts:131`. `refreshProgress` reads like an action but is an async factory returning a `Channel`; every call site is `await refreshProgress()` passed as an argument. `createProgressChannel` (or similar) states the role.
4. **Test-fixture coupling (follow-up)** — `src-tauri/src/core/tests/manifest.rs:40` asserts `base.had_frontmatter == case.meta.is_some()` over the shared corpus. That identity only holds because the corpus contains no *present-but-empty* frontmatter case, where Rust (`had_frontmatter: true`) and the TS adapter (`meta: null`, by the pre-existing `keys.length === 0` rule) legitimately disagree. The coupling is invisible today and will mislead whoever adds `---\n---\nBody` to the corpus. Derive expectation per language instead of equating them.
