## Concrete interface and timing

- New registered/annotated command `update_managed_skill(skill_id, policy, on_progress)` → `SkillMutationResultDto { report: RefreshReportDto, skills: Vec<ManagedSkillDto> }`. Generated frontend call: `updateManagedSkill(skillId, policy, onProgress)`.
- Update and Restore both call this command. It delegates to the existing `refresh_managed_skills` command as `Some(vec![skill_id])`, awaits the whole operation (including reassert), and composes the complete catalog in `spawn_blocking`. No copied acquisition pool, settlement, guard, or auto-sync policy.
- `repoint_local_skill_source` and `repoint_git_skill_source` now return the same `SkillMutationResultDto`. Their existing core operation finishes before `SkillMutationResultDto::from_report` reads the catalog.
- Edit returns `InvocationEditResultDto { report: InvocationEditReportDto, skills }`, where its report is `{ skill_id, skill_name, propagation: Vec<PropagationTargetDto> }`. Core's existing `InvocationEditOutcome { entry, propagation }` is unchanged. The command uses the entry only for report identity/name; `skills` comes from a new complete read, never the returned entry.
- `managed_skill_dtos` reuses `managed_skill_catalog` and `ManagedSkillDto::from`, also serving the unchanged `get_managed_skills` command. Constructors propagate catalog failures with `?`; they do not manufacture `skills: []`.
- Catalog assembly occurs outside the Mutation guard after the operation returns. It is a fresh post-operation read, **not** a transaction across database/filesystem/acquisition. Concurrent later changes can appear, intentionally. No full catalog scan was added inside core Edit's guarded single-entry read.
- Generated bindings were regenerated by `cargo test ... export_bindings`, reviewed and subsequently regenerated by the complete gates. `lib.rs` changes only the new command registry entry. Skills shim adds only the three mutation DTO exports.
