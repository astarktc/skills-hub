## B1 — `core/content_identity.rs`: one supplier of a Managed skill's hash (#1; Q2, Q14, Q15)
Today `skills.content_hash` is written under different rules by `install_finalize::compute_content_hash`, `skill_edits::record_hash`, and `project_sync::observe_assignment`'s read-time backfill (`:497-512`), while `global_sync::target_has_same_content` re-hashes both sides ignoring the row, and Propagation threads `content_hash: Option<&str>` through three signatures. v1.2.9 D1 made the supply honest; this item makes it one module.
→ New module `content_identity` absorbing `content_hash.rs` (`hash_dir` becomes private implementation; `skill_files::is_ignored` stays the one ignore predicate — fold the `.skills-hub-manifest-` prefix into it or document in `is_ignored` why hashing needs it and `skill_files` must not skip it; backlog 14). Interface (three doors, your exact signatures):
  - **record** — hash a freshly landed central copy and write it to the skill row (finalize + Edit replay call this; they stop computing themselves);
  - **read** — the hash for a skill id/record: return the stored one, else compute + backfill, else `None` on an I/O failure (warn-logged once). This replaces `project_sync`'s backfill-during-read and is what Propagation asks;
  - **same-content** — "do these two directories have the same identity" for global sync's overwrite check (keeps re-hashing the target; the source side goes through **read**).
`propagate_unlocked` / `propagate_project_rows` / `propagate_one_assignment` drop the `content_hash` parameter and ask **read** once per propagation (not per target). `UpdateOutcome.content_hash` and `RefreshReport`'s per-skill hash keep their shape (read from the row). Nothing else may call `hash_dir`. `sync_status::next_status` unchanged.
Tests: move `content_hash` tests over; **read** backfills a missing hash exactly once (second read hits the row — count via a store spy or SQL trigger); I/O failure → `None`, status unchanged (`obs.current`); Propagation of a skill whose row lost its hash still records `Some` on copy rows and reconcile reports `Synced`; backlog 15: replace the 30 s `try_serialized` poll in `tests/propagation.rs:512-525` with a deterministic seam. Existing propagation/project_sync/global_sync tests pass unchanged in behaviour.

## B2 — `core/skill_update.rs`: Update is one module (#2; Q3, Q4, Q16, Q17, Q18)
Today the tail is composed by hand in `installer::finalize_and_propagate_unlocked` (`:376-400`); local Re-point (`unlocatable::repoint_and_update` `:83-133`) writes `source_ref` before the batch runs (non-atomic); `skill_edits::set_invocation_override` (`:80-146`) re-implements finalize→propagate and **logs** propagation failures (`:132-139`) — the only breach of the fan-out rule; `AcquiredUpdate` is a record snapshot taken outside the guard that nothing re-admits at apply time.
→ New module `skill_update` with one entry (under the guard, i.e. an `_unlocked` seam called by Refresh's apply phase and by the Edit command's own `serialized` body): "settle this Managed skill's central copy from **these bytes** and bring its targets in line" → `UpdateOutcome`. Bytes arrive through an adapter enum with four variants: git-acquired Staging dir (+ new revision, + optional re-pointed source), local folder (Re-point/Update from a local source — the module stages it), edit-in-place (no new bytes; run the settle step over the current central copy), restore-rebuild (central copy absent — the existing Restore path). Body = the D2 `finalize_update` + settle closure + Propagation, with **content_identity::record** as the hash step.
  - **Admission (Q4):** before landing, compare the acquired result to the *current* row (`get_skill_by_id` under the guard): row gone → per-skill `Skipped { reason: SkillGone }`; row's `source_ref`/`source_subpath`/`source_type` differ from what acquisition read (and the adapter does not itself carry a re-point) → `Skipped { reason: StaleAcquisition }`; staged bytes discarded in both. New `SkillRefreshStatus` variants (+ DTO mirror in `commands/mod.rs`, + `describeCommandError` is NOT involved — these are report data; add the two i18n keys the frontend will need under the existing skipped-reason family, `en` + `zh`, but do not wire UI). Existing acquire-first rule holds: no upsert before the module's finalize.
  - **Local Re-point (Q17):** the new `source_ref` rides in the record the adapter hands over — as git Re-point already does (`installer.rs:341-346`) — so `repoint_local_source`'s pre-write goes away; a failed local Re-point leaves the old source and old bytes. `unlocatable.rs` keeps validation + constructs the adapter.
  - **Edit write (Q18):** `set_invocation_override` becomes: guard → write the override row → call `skill_update` with the edit-in-place adapter → return `{ entry: ManagedSkillEntry, propagation: <the same propagation report DTO Update returns> }`.
